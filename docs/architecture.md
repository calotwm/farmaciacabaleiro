# Farmacia Cabaleiro — Architecture

Inventory management for a single pharmacy: product catalog, lot-based stock with expiry control (FEFO),
suppliers and scheduled deliveries, goods receiving, notifications, reports and audit.

## 1. Style

Modular monolith, hexagonal per module. One Next.js (App Router) app plus a separate worker process
for scheduled jobs. One PostgreSQL database.

```
src/
  app/                    Next.js routes (thin: parse input, call use cases, render)
  modules/<module>/
    domain/               Pure TypeScript: entities, value objects, rules. No Prisma/Next imports.
    application/          Use cases and ports (interfaces). Orchestrates domain + ports.
    infrastructure/       Adapters: Prisma repositories, email, push, etc.
    ui/                   Container (data/actions) and presentational components.
  shared/
    domain/               Dates/timezone, money, expiry status, domain errors.
    application/          Cross-cutting application helpers (error -> user message).
    config/               Zod-validated environment.
    infrastructure/db/    Prisma client factory.
  worker/                 node-cron process (daily alert rules)
prisma/                   Schema, migrations, seed
```

Dependency rule: `domain` <- `application` <- `infrastructure` / `ui` / `app`. Domain never imports outward.
Business rules are enforced on the server; the UI is never the only guard. UI copy is neutral Spanish (es-AR);
code, identifiers, comments and docs are English.

## 2. Data model overview

Defined in `prisma/schema.prisma` (snake_case tables, UUID ids generated by Postgres).

- Access: `Role`, `Permission`, `RolePermission`, `User`, `Session`, `PasswordResetToken`, `AuditLog`.
- Catalog: `Category`, `Unit`, `Product`.
- Inventory: `Lot`, `StockMovement`, `AdjustmentReason`, `StockCount`, `StockCountLine`.
- Suppliers and deliveries: `Supplier`, `SupplierProduct`, `ScheduledDelivery`, `DeliveryExpectedItem`.
- Receiving: `Receipt`, `ReceiptLine`, `ReceiptIssue`.
- Notifications: `AlertEvent`, `Notification`, `NotificationPreference`, `UserNotificationSettings`,
  `PushSubscription`, `NotificationDelivery` (outbox).
- Settings: `Setting` (key/value JSON).

## 3. Key invariants

1. **Stock lives in lots.** A product has no stock column. Physical, available and blocked stock are derived
   by summing its lots (`current_quantity`, `blocked_quantity`; available = current - blocked, excluding
   expired/blocked/quarantine lots). CHECK constraints keep quantities non-negative and
   `blocked_quantity <= current_quantity`.
2. **Movements are append-only.** `stock_movements` rejects UPDATE, DELETE and TRUNCATE through a Postgres
   trigger. Corrections are compensating movements, never edits — even for admins.
3. **No negative stock, no override.** Exits are validated against the lot inside the same transaction.
4. **Expired lots** only allow write-off or return with a reason; they are never dispensed.
5. **Idempotency.** Receipt confirmation is keyed by `Receipt.idempotencyKey` (unique); `AlertEvent` is unique on
   (rule, entity type, entity id, threshold key, event date), so a repeated worker run creates nothing new.
6. **Notification failures never roll back business transactions.** External channels go through the
   `NotificationDelivery` outbox processed by the worker.
7. **Authorization on the server.** Every server action and route handler calls `requireUser()` /
   `requirePermission(key)`; middleware only does a cheap cookie-presence redirect.

## 4. Dates and timezone rules

Implemented in `src/shared/domain/dates.ts`; tested with the server TZ forced to UTC, Asia/Tokyo and
America/Los_Angeles.

- The pharmacy timezone is `America/Argentina/Buenos_Aires` (UTC-3, no DST). It is a constant default now and
  will be read from the `locale.timezone` setting later.
- **Calendar dates** (lot expiry, event dates) are plain `YYYY-MM-DD` strings (`CalendarDate`) in the domain and
  `DATE` columns in Postgres. They carry no zone, so they never shift. Prisma returns DATE as a `Date` at
  UTC midnight; use `fromDbDate` / `toDbDate` at the boundary.
- **Instants** (movements, receipts, sessions) are `timestamptz` and are rendered in AR time with
  `formatDateTime`.
- **"Today"** is `todayInTz(now)`: the calendar date in the pharmacy timezone, never the server's.
- A lot **expires at the end of its stated day**: valid through the expiry date, expired from the next day.
  `MM/AAAA` input maps to the last day of that month (`expiryFromMonthYear`).
- Display format is `DD/MM/AAAA` (and `HH:mm` 24h). Money is `es-AR` / `ARS` by default (`formatMoney`).

### Expiry status

`assessExpiry(expiryDate, today, { thresholds, criticalDays })` in `src/shared/domain/expiry-status.ts`:

| Status | Rule |
| --- | --- |
| `EXPIRED` | today is after the expiry date |
| `CRITICAL` | days left <= 30 (`criticalDays`, includes the expiry day itself) |
| `WARNING` | days left <= largest threshold (default 180) |
| `NORMAL` | otherwise |

Default thresholds are `[180, 90, 60, 30, 7]`. `crossedThreshold` is the smallest threshold greater than or equal
to the days left (the alert bucket the lot is in), or `null`.

## 6. Errors

`src/shared/domain/errors.ts` defines `DomainError` and subclasses (`NotFoundError`, `ForbiddenError`,
`UnauthenticatedError`, `ValidationError`, `ConflictError`, `RateLimitError`). They are mapped to Spanish messages
at the edge by `toUserMessage` (`src/shared/application/user-message.ts`); unknown errors never leak internals.

## 7. Authentication and authorization

Module `src/modules/auth` (hexagonal: `domain` policies, `application` services + ports, `infrastructure` adapters,
`ui` forms/actions). Audit entries go through `recordAudit` in `src/modules/audit`.

- **Passwords**: argon2id (`@node-rs/argon2`, OWASP cost profile), minimum 10 characters.
- **Sessions**: random 32-byte token in the `fc_session` cookie (httpOnly, SameSite=Lax, Secure in production);
  only its SHA-256 hash is stored in `sessions`. Idle timeout 12 h (sliding, refreshed at most every 5 min),
  absolute lifetime 7 days. Logout deletes the row; deactivating a user, changing a role or resetting a password
  deletes all of that user's sessions. The cookie cannot slide in Server Components, so it only caps the absolute
  lifetime; the DB row is authoritative.
- **Guards**: `src/middleware.ts` only checks cookie presence and redirects to `/login`. Real validation is
  `getCurrentUser()`, `requireUser()` and `requirePermission(key)` (`src/modules/auth/server.ts`), called by every
  server action. Use cases also call `assertPermission(actor, key)`, so the rule holds outside Next.js. Permissions come
  from Role -> RolePermission; the `admin` role has all of them.
- **Login rate limit**: 5 failed attempts per email + IP in 15 minutes, counted from `auth.login.failed` audit entries
  (no extra table). Failures return the generic "Email o contraseña incorrectos"; unknown emails still run a password
  hash to keep timing similar. The client IP comes from `x-forwarded-for`: the production proxy must set it.
- **Password reset**: token hash stored (1 h, single use, a new request invalidates older links), sent through the
  `EmailSender` port (`ConsoleEmailSender` by default, `SmtpEmailSender` when all `SMTP_*` are set). The response is
  identical whether or not the email exists. Resetting revokes every session.
- **Bootstrap**: `pnpm admin:create`. The last active admin cannot be demoted or deactivated, and nobody can
  deactivate themselves.
- **Audit actions**: `auth.login.success|failed|blocked`, `auth.logout`, `auth.password_reset.requested|completed`,
  `user.create`, `user.role.change`, `user.activate`, `user.deactivate`.

## 8. Catalog

Module `src/modules/catalog` (products, categories, units). Pages: `/productos` (list, detail, new, edit),
`/configuracion/categorias`, `/configuracion/unidades`.

- **Permissions**: `products.read` (list/view), `products.write` (create/edit), `products.archive`,
  `catalog.manage` (categories and units). Pages show "Acceso denegado" and every use case calls `assertPermission`.
- **Product code**: `code` is the unique internal code. When the form leaves it empty a `P-XXXXXXXX` code is generated
  (retried on collision). Barcode and SKU are optional and unique; duplicates fail with a field-level Spanish message
  (`ConflictError.fieldErrors`).
- **Pharmacological fields are optional**: a non-medication product only needs name, category and unit.
- **Archive**: `ARCHIVED` products are hidden from lists unless the status filter asks for them and cannot be edited
  until unarchived. Inactive categories/units cannot be newly assigned but keep working for products that already use them.
- **Categories and units**: create, rename (case-insensitive unique), activate/deactivate, delete only when no product uses
  them (a DB foreign key is the last line of defence). Migration `unit_active` added `units.active` (categories already had it).
- **Tables**: search, filters, sort and pagination are server-side and live in the URL (`src/shared/application/list-query.ts`,
  `Pagination`, `SortableHead`). Filter forms are plain GET forms and work without JavaScript.
- **Barcode input** (`src/components/barcode-input.tsx`): USB keyboard-wedge scanners type fast and end with Enter. With
  `onScan` the Enter does not submit the form (product form: moves focus on); without it, Enter submits the surrounding form
  with the cleaned code (`normalizeBarcode`). In the product list a barcode that matches a product opens it directly.
- Suppliers do not exist as a module yet: products reference them through a read-only `SupplierLookup` port.

## 9. Inventory: lots and stock movements

Module `src/modules/inventory`. Pages: `/lotes` (list, `/lotes/[id]` detail with history), `/movimientos` (immutable history),
`/movimientos/nuevo` (fast flow and manual lot entry), stock breakdown and FEFO table on `/productos/[id]`.

**Domain (pure, unit-tested)**
- Effective lot state: `EXPIRED` when today > expiry date (whatever is stored), else the stored status.
  A lot is usable for normal exits only if effectively `AVAILABLE`.
- Stock breakdown derived from lots (no counter): each unit lands in exactly one bucket. Expired lot -> `expired`; `QUARANTINE` /
  `BLOCKED` lot -> `blocked` (all units); otherwise `blockedQuantity` is `blocked`. `available = physical - blocked - expired`
  (the spec formula would double count a quarantined lot that also has blocked units, or a quarantined expired lot).
- FEFO allocator: earliest expiry, then `receivedAt`, then lot number; usable units only (on hand minus blocked);
  `InsufficientStockError` states the available quantity.
- Movement planners (`movement-rules.ts`) turn "current lots + command" into new lot state + movements, or throw.
  Quantities are positive integers (1..1,000,000); direction comes from the type.

| Type | Permission | Rules |
| --- | --- | --- |
| `ENTRY` | `inventory.write` | Creates the lot, or adds to the lot with the same number and expiry. New lots cannot be already expired. Archived products cannot receive stock |
| `EXIT` | `inventory.write` | Usable lots only; FEFO by default, or a chosen lot that must itself be usable. Never takes blocked units |
| `ADJUSTMENT_IN/OUT` | `inventory.write` | Reason required; not on expired lots |
| `RETURN`, `WRITE_OFF` | `inventory.writeoff` | Reason required; the only types (with count corrections) an expired lot accepts |
| `BLOCK` / `UNBLOCK` | `inventory.write` | Reason required. Block some units, or put the whole lot in quarantine/blocked; unblock units or the lot. Not on expired lots |

Removals (adjustment out, write-off, return) may take blocked units too (a quarantined lot is what usually gets written off);
the blocked counter is clamped to what remains. A lot reaching 0 becomes `DEPLETED`; a depleted lot that receives stock is
`AVAILABLE` again.

**Transaction and concurrency.** Every operation is ONE Prisma transaction: lock the product row
(`SELECT ... FOR NO KEY UPDATE`), read its lots (after the lock, so the values are current), plan, update lots, append movements.
Locking the product serializes all stock operations on it, so two concurrent exits can never drive a lot negative (covered by an
integration test with `Promise.all`). The DB CHECK constraints are the last line of defence.

**Alerts.** After the commit, outside the transaction, `StockLevelAlerts.evaluate` (port, Prisma adapter) computes the available
stock; `available <= minStock` creates a `LOW_STOCK` `AlertEvent` (`OUT_OF_STOCK` when nothing is available) keyed by
product + rule + AR date, plus one `Notification` per active user that can read inventory. Both inserts ignore conflicts, so a
repeated evaluation creates nothing. Failures are logged and swallowed: they never undo a movement. T4 reuses/extends the port.

**Audit.** Every operation writes `stock.<type>` (entity `product`) with the movements, reason and, for entries, the lot.

**Reasons.** `reasonId` must belong to the catalog kind of the type (adjustment / write-off / return); `reasonText` is free text.
Reason-requiring types accept either.

**Testing approach.** `stock_movements` is append-only, so anything that ever had a movement cannot be deleted. Integration tests
run inside one transaction that is always rolled back (the module is built with the outer transaction as reader and
`TransactionRunner`), so nothing is left behind. The concurrency tests need real transactions and commit: they use one
`TEST-<uuid>` product, a permanent inactive test user and disabled alerts, so no notification reaches real users. E2E products are
named `E2E ...`; those with movements stay in the dev database and the E2E admin is deactivated instead of deleted.

## 10. Physical counts

Pages `/conteos` (list, open) and `/conteos/[id]`. Permission: `inventory.count` for everything; **closing also needs
`inventory.write`** (reconciliation adjusts stock, and the seed has no separate "adjust" permission).

- **Open**: snapshots every lot with units on hand, optionally limited by category and/or location (a substring of the lot or
  product location). The scope is written to the notes of the count. An empty scope is rejected.
- **Count**: one number per lot (blank = not counted); the difference (counted - expected) is live in the browser and everything is
  saved in one request; a barcode scan moves the cursor to the lot of that product. Movements are still allowed while a count is open.
- **Close** (one transaction): the count row is locked (`FOR UPDATE`), the affected products are locked in id order, and each counted
  lot gets a compensating `COUNT_CORRECTION_IN` / `COUNT_CORRECTION_OUT` movement for `counted - CURRENT quantity`
  (`referenceType = stock_count`, `referenceId = count id`) with the required reason. Using the current quantity instead of the
  snapshot means a movement registered while the count was open is never counted twice. Lots nobody counted are left untouched.
  A second (or concurrent) close finds the count closed and fails with a conflict; a closed count is read-only.
- Lots counted while expired are corrected too and keep their expired state (the date decides it). A lot counted down to 0 becomes
  `DEPLETED`; stock found in a depleted lot revives it.
- Migration `count_correction_direction` added `COUNT_CORRECTION_IN/OUT` to `stock_movement_type`: the original
  `COUNT_CORRECTION` had no direction and movements store a positive quantity. The old value stays in the enum (never written).

## 11. Suppliers

Module `src/modules/suppliers`. Pages: `/proveedores` (list), `/proveedores/nuevo`, `/proveedores/[id]` (detail), `/proveedores/[id]/editar`.

- **Permissions**: `suppliers.read` (list/view; admin and employee) and `suppliers.write` (create, edit, activate/deactivate, supplied
  products; **admin only** by seed: supplier master data is a purchasing decision). Pages show "Acceso denegado" and every use case
  calls `assertPermission`. The employee role also gets `deliveries.write` (see section 12 onwards) through the seed.
- **CUIT** (`domain/cuit.ts`): optional and unique. Validated as 11 digits with a known AFIP prefix and the modulo-11 check digit
  (remainder 0 -> 0; a remainder that would give 10 is rejected). It is stored as the 11 digits and shown as `XX-XXXXXXXX-X`, so a
  search matches whatever separators the user typed. Duplicates fail with a field error on `cuit` (also when two inserts race).
- **Visit days** are ISO weekdays in `suppliers.visit_days` (1 = Monday ... 7 = Sunday), edited as a checkbox group. Delivery hours are
  free text; the lead time is whole days (0..365).
- **Status**: `INACTIVE` suppliers keep their history but are not offered when scheduling deliveries or receiving goods. There is no
  delete (deliveries, receipts and lots reference suppliers).
- **Supplied products** (`supplier_products`): add by text search or barcode scan (`ProductPicker`, backed by the
  `searchProductsAction` server action: exact barcode first, otherwise name/ingredient/brand/code/SKU), remove with confirmation. Archived
  products cannot be added; a product can be linked once. Adding or removing is audited on the supplier.
- **Audit actions**: `supplier.create|update|activate|deactivate`, `supplier.product.add|remove`.
- **Forms with checkbox groups**: `parseForm(schema, formData, { arrayFields })` collects repeated fields into arrays and `formValues`
  echoes them joined by commas.

## 12. Accepted assumptions

1. A lot expires at the end of the stated day; `MM/AAAA` means the last day of the month.
2. Expired lots only allow write-off/return with a reason.
3. No negative stock and no override.
4. Corrections use compensating movements, even for admins.
5. Single tenant, no POS integration.
6. Zero budget: anything paid is replaced by a free alternative or skipped and documented.

## 13. Decisions (ADR-style)

| # | Decision | Why |
| --- | --- | --- |
| 1 | Modular monolith, hexagonal modules | One deployable, clear boundaries, testable domain |
| 2 | Own auth with DB sessions and argon2id | No paid IdP; revocable sessions; hashes only in DB |
| 3 | Stock derived from lots | Single source of truth, FEFO and expiry per lot |
| 4 | Append-only movements enforced in Postgres | Audit integrity independent of app bugs |
| 5 | Expiry as DATE, instants as timestamptz | No timezone drift in expiry logic |
| 6 | Calendar dates as strings in the domain | Zone-free, trivially comparable, server-TZ independent |
| 7 | Separate worker process (node-cron) | Daily jobs without coupling to web requests |
| 8 | Outbox for push/email | External failures cannot roll back business transactions |
| 9 | Prisma 7 with the `pg` adapter | Current Prisma architecture; one driver for app and tests |
| 10 | Login rate limit counted from the audit log | No extra table; failures are audited anyway |
| 11 | Railway proxy cert is self-signed | Dev-only `DATABASE_SSL_REJECT_UNAUTHORIZED=false`; production uses private network or verified TLS |
| 12 | `isDomainError` / `hasErrorCode` instead of `instanceof` at module edges | Next.js can bundle `errors.ts` once per layer (RSC, server actions); class identity then differs and `instanceof` silently fails |
| 13 | Form state echoes submitted values (never password/token fields) | React 19 resets uncontrolled forms after an action; users must not lose what they typed on a validation error |
| 14 | Product row lock (`FOR NO KEY UPDATE`) to serialize stock operations | Simple, deadlock-free (one lock per operation), exact; per-lot conditional updates cannot express "current - blocked >= q" |
| 15 | Planners are pure functions over lot state | The same FEFO plan runs in the browser preview and on the server, and is unit-testable without a database |
| 16 | Count corrections computed against the current lot quantity | Snapshot-based deltas would double count movements made while the count is open |
| 17 | `COUNT_CORRECTION_IN/OUT` instead of a signed quantity | `stock_movements.quantity > 0` is a DB CHECK and direction comes from the type everywhere else |
| 18 | CUIT stored as 11 digits, formatted at the edge | Search and uniqueness are independent of separators |
| 19 | Supplier master data is admin-only (`suppliers.write`); employees read | Purchasing decisions stay with the owner; employees still schedule deliveries and receive goods |
